# 1. 문서 개요

## 1.1 문서 목적
본 문서는 **Smart Edu Platform(개인화된 학습 관리 앱)** 의 기능적 요구사항과 품질 속성을 만족하기 위한 시스템 아키텍처의 기본 구조와 설계 원칙을 정의하기 위한 문서이다. 

본 플랫폼은 초등학생부터 시니어층까지 전 연령대를 아우르는 폭넓은 사용자를 수용해야 하며, 각 페르소나의 학습 목적(내신, 수능, 취업, 자격증, 치매 예방 등)에 맞는 맞춤형 기능을 제공해야 한다. 이를 위해 본 문서에서는 구현 명확성과 유지보수성을 극대화할 수 있는 아키텍처 설계 방향을 제시한다.

## 1.2 아키텍처 기본 원칙
본 시스템 아키텍처는 다음의 핵심 원칙을 기반으로 설계되었다.

| 원칙 | 설명 |
|---|---|
| **동적 UI 대응성** | 사용자의 페르소나 정보에 따라 시스템의 화면 구성 요소와 테마가 유연하게 변경될 수 있도록 프론트엔드 컴포넌트를 모듈화한다. |
| **비동기 자원 관리** | 대형 언어 모델(LLM) 연동과 같이 대기 시간이 발생하는 외부 API 통신 시, 클라이언트의 사용자 경험(UX)이 중단되지 않도록 비동기 제어 흐름을 전 계층에 적용한다. |

# 2. 아키텍처 스타일 및 패턴 

소프트웨어 공학의 검증된 원칙에 의거하여, 본 플랫폼은 구현이 명확하고 유지보수가 용이한 복합 아키텍처 패턴을 채택한다.

## 2.1 클라이언트-서버 아키텍처
시스템을 사용자 인터페이스를 전담하는 '모바일 클라이언트'와 비즈니스 로직 및 데이터를 처리하는 '백엔드 응용 서버'로 명확히 분리한다.

* **Thin Client 전략:** 모바일 기기의 환경과 사용자 경험을 고려하여 클라이언트의 연산 부담을 최소화한다. 크기가 큰 데이터의 가공, 통계 산출, 외부 API와의 통신 등 무거운 연산과 데이터 관리 부담은 모두 백엔드 서버가 전담하고, 클라이언트는 렌더링과 사용자 입력 이벤트 처리에 집중한다.
* **표준 RESTful API 통신:** 클라이언트와 서버는 HTTP/HTTPS 기반의 정형화된 REST API 인터페이스를 통해 소통한다. 이를 통해 상호 간의 의존성을 줄이고, 자원 독립성을 확보한다.

## 2.2 단일 구조 계층형 아키텍처 
백엔드 서버 내부의 복잡도를 낮추고 소스코드의 응집도를 높이기 위해, 역할을 기준으로 3개의 논리적 계층(Layer)을 엄격히 분리한다. 상위 계층은 인접한 하위 계층만 호출할 수 있도록 제한하여 코드의 가독성과 수정 용이성을 보장한다.

| 계층 (Layer) | 역할 및 특징 |
|---|---|
| **표현 계층**<br>(Presentation / Controller) | 클라이언트의 HTTP 요청을 가장 먼저 받아들이는 진입점이다. 입력 데이터의 유효성을 검증하고, 비즈니스 로직을 호출한 뒤, 그 결과를 규격화된 JSON 형태로 클라이언트에 반환한다. |
| **비즈니스 로직 계층**<br>(Business Logic / Service) | 플랫폼의 핵심 가치와 요구사항을 실현하는 계층이다. 일정 관리 상태 변경, 순공 시간 누적 계산, AI 프롬프트 생성 가공 등 실제 도메인 규칙을 수행하는 로직이 이 계층에 집중된다. |
| **데이터 접근 계층**<br>(Data Access / Repository) | 데이터베이스와의 직접적인 데이터 입출력(CRUD)을 전담한다. 상위 계층의 비즈니스 로직이 데이터베이스 시스템 종류에 종속되지 않도록 추상화된 데이터 접근 인터페이스를 제공한다. |

## 2.3 프론트엔드 MVC (Model-View-Controller) 패턴
자바스크립트(웹) 기반에 적합한 MVC 패턴을 도입하여, React Native 환경에서 단일 코드베이스로 모바일 어플리케이션을 효율적으로 빌드하고 유지보수성을 높인다.

* **Model (상태 데이터):** 현재 로그인한 사용자의 페르소나 타입, 오늘의 스톱워치 측정 시간, 칸반 보드 일정 목록 등 전역/로컬 상태 데이터를 관리한다.
* **View (UI 컴포넌트):** 사용자에게 보여지는 화면이다. 자체적인 비즈니스 로직을 가지지 않으며, Model의 데이터 변화를 감시하여 화면을 동적으로 그려낸다.
* **Controller (이벤트 핸들러):** 사용자의 버튼 터치, 입력 폼 제출 등의 이벤트를 받아 Model의 데이터를 변경하거나 백엔드 서버에 API 요청을 보내는 제어 역할을 담당한다.

# 3. 시스템 논리 구조 및 서브시스템 분할

## 3.1 3-Tier 물리적 구조 정의
본 플랫폼은 개발 인프라 구축 비용을 최소화하고 안정적인 운영을 위해 가장 대중적이고 표준적인 3티어(3-Tier) 구성을 가진다.

| Tier | 적용 기술 | 구성 및 역할 |
|---|---|---|
| **Client Tier** | React Native | 하나의 소스코드로 안드로이드와 iOS 앱을 동시에 빌드할 수 있는 모바일 어플리케이션 환경을 구성한다. |
| **Application Server Tier** | Node.js (Express) | 단일 웹 서버 프로세스 내에서 모든 비즈니스 도메인을 처리하는 효율적인 모놀리식 구조를 채택한다. |
| **Database Tier** | RDBMS 중심 검토<br>(MySQL / PostgreSQL 등) | 사용자 계정, 일정, 게시판, 학습 기록 등 관계형 데이터가 중심이 되므로 **RDBMS(MySQL 또는 PostgreSQL)** 도입을 우선적으로 검토한다. 단, AI 생성 퀴즈나 비정형 데이터는 유동적인 문서형 데이터 저장이 가능한 **MongoDB**의 장점이 있으나 구현 복잡도가 증가할 수 있다. 따라서 2단계 구현 진입 전 팀 논의를 거쳐 최종 DBMS 아키텍처를 확정한다. |

## 3.2 핵심 서브시스템(모듈) 분할 명세
요구사항 명세서의 기능적 요구사항(FR)을 기준으로 백엔드 서버의 도메인을 역할 단위의 서브시스템 모듈로 분할하여 독립성을 확보한다.

### 3.2.1 사용자 관리 모듈 (Auth/User Module)
* **주요 역할:** 회원가입, JWT 기반 로그인, 사용자 프로필 관리, 관리자의 사용자 계정 제재(FR-28).
* **구현 전략:** 사용자가 로그인에 성공하면 서버는 암호화된 JWT 사원증 토큰과 함께 페르소나 설정값을 클라이언트에 전달하여 전반적인 앱 테마를 구성하도록 지원한다. 관리자 권한을 통해 불량 사용자를 제재하는 로직을 포함한다.

### 3.2.2 AI 스마트 학습 모듈 (AI Learning Module)
* **주요 역할:** 외부 AI API 또는 내부 AI Service 시스템과 연동하여 **AI 학습 질의, AI 오답노트 생성, 학습 추천, AI 기반 퀴즈 생성, 학습 내용 요약** 기능을 전담하는 핵심 모듈이다.
* **구현 전략:** 사용자의 비정형 노트를 파싱하여 정교하게 설계된 프롬프트와 함께 AI 시스템으로 전송한다. Node.js의 기본 비동기 구문을 활용하여 AI 결과가 반환될 때까지 대기한 뒤 일괄 저장한다.

### 3.2.3 일정 및 태스크 관리 모듈 (Schedule/Task Module)
* **주요 역할:** 학습 일정 관리, 칸반 보드 상태 관리, 마감일 알림, **외부 캘린더 시스템(External Calendar System) 연동**.
* **구현 전략:** 애플리케이션 내부 일정 관리뿐만 아니라, Google Calendar, Apple Calendar API 등과 연동하여 학습 일정을 동기화한다. **Thin Client 기조에 맞추어 데이터의 보관 및 통계 분석 부담은 서버가 전담**하여 모바일 기기의 부하를 방지한다.

### 3.2.4 집중 및 통계 모듈 (Focus/Statistics Module)
* **주요 역할:** 앱 차단 모드, 스톱워치/타이머 측정, 학습 데이터 및 히트맵 시각화.
* **구현 전략:** 데이터의 집계 및 보관 책임(서버)과 화면 렌더링 책임(클라이언트)을 분리한다. 타이머의 초 단위 카운팅 자체를 서버에서 실행하면 자원 소모가 발생하므로 클라이언트에서 카운팅하되, 측정된 시간 정보의 누적 관리 및 통계 산출 부담은 모두 서버로 위임한다.

### 3.2.5 커뮤니티 및 관리자 모듈 (Community/Admin Module)
* **주요 역할:** 주간 학습 랭킹, 커뮤니티 게시판 이용, 관리자의 게시판 관리, 스터디 챌린지 생성 및 관리(FR-29).
* **구현 전략:** 랭킹 시스템의 즉각적인 반영은 사용자의 강력한 동기부여 요소로 작용한다. 이를 위해 완전한 실시간 동기화(웹소켓 유지)에 따른 서버 과부하를 방지하면서도 실시간성을 보장할 수 있도록, **1~2분 주기의 짧은 백그라운드 동기화(Short Polling 또는 SSE 방식)**를 채택하여 DB 부하와 사용자 경험 사이의 최적의 합의점을 도출한다.

### 3.2.6 접근성 지원 모듈 (Accessibility Module)
* **주요 역할:** 큰 글씨/고대비 모드 제어, STT 변환, 초등학생 친화 UI 제공, 반복 복습 알림 로직 제공.

## 3.3 아키텍처 모듈과 요구사항 추적표
설계된 아키텍처의 각 모듈이 담당하는 기능적/비기능적 요구사항(FR/NFR)의 매핑 관계는 다음과 같다.

| 아키텍처 모듈 | 주요 기능 | 관련 요구사항 ID |
|---|---|---|
| **Auth/User Module** | 회원가입, 로그인, 사용자 계정 관리 및 제재 | FR-01, FR-02, FR-28, NFR-02, NFR-03 |
| **Schedule/Task Module** | 일정/칸반 보드 관리, 마감일 알림, 외부 캘린더 연동 | FR-03, FR-04, FR-05, FR-22 |
| **AI Learning Module** | AI 질의, 오답노트, 추천, 퀴즈 생성, 요약 | FR-07, FR-08, FR-09, FR-10, FR-19 |
| **Community/Admin Module** | 랭킹, 챌린지 관리, 게시판, 운영 관리 | FR-11, FR-12, FR-13, FR-27, FR-29 |
| **Focus/Statistics Module** | 앱 차단, 타이머, 학습 데이터/히트맵 시각화 | FR-14, FR-15, FR-16, FR-17 |
| **Accessibility Module** | 큰 글씨/고대비, STT, 초등학생 UI, 복습 알림 | FR-20, FR-21, FR-25, FR-26 |

# 4. 비기능적 요구사항(NFR) 충족을 위한 아키텍처 전략

아키텍처 설계의 최종 목표는 비기능적 요구사항의 달성에 있다. 본 설계는 시스템 인프라를 단순화하면서도 아래의 품질 전략을 통해 앱의 안정성을 확보한다.

| 품질 속성 | 적용 전략 | 상세 설명 |
|---|---|---|
| **성능 및 응답성** | Non-blocking I/O 활용 | 외부 AI 모델과 통신할 때 발생하는 긴 대기 시간 동안 서버가 멈추는 것을 방지하기 위해, 백엔드 로직 전체에 자바스크립트의 `async/await` 구문을 적용한다. |
| **사용자 경험(UX)** | 대기 시간 명시적 안내 | AI 연산이 길어질 경우 로딩 스피너와 함께 **'예상 소요 시간(예: 약 15초 남음)'**을 명시적으로 안내하여 사용자의 혼란과 이탈을 방지한다. |
| **보안성** | 패스워드 암호화 | 사용자의 비밀번호는 텍스트 그대로 저장하지 않으며, 전 세계 표준 보안 라이브러리인 `bcrypt`를 활용하여 단방향 해시 암호화 처리를 거친 후 적재한다. 모든 통신은 HTTPS로 제한한다. |
| **데이터 보호** | 접근 제어 (Isolation) | 클라이언트가 데이터베이스에 임의로 접근하는 통로를 원천 차단하고, 인증 필터(JWT)를 통과한 검증된 요청만 비즈니스 레이어를 거치도록 격리성을 강화한다. |
| **이식성 및 효율성** | 크로스 플랫폼 개발 | 프론트엔드를 웹 표준 기반의 React Native 구조로 개발하여 단일 소스코드 제어를 실현하고, 향후 플랫폼 확장 시 앱을 쉽게 이식할 수 있는 유연성을 확보한다. |
