## 2026년 05월 18일 월요일

---

## 1. 회의 목적

PR #16 병합 이후 2단계 초기 프로젝트 세팅 상태를 확인하고, 본격적인 기능 구현 전 남은 환경 구축 요소와 1단계 제출 문서 점검 방향을 논의함.

연결된 Issue #14가 닫혔고, 조원들이 로컬 세팅을 진행한 상태이므로 이후 작업 순서와 문서 정리 범위를 확인함.

---

## 2. 2단계 초기 환경 구축 상태 확인

PR #16 merge 이후 `src/frontend`와 `src/backend`의 초기 프로젝트 세팅이 완료됨.

조원들은 각자 로컬 환경에서 프로젝트 실행 및 기본 세팅을 확인함. 남은 환경 구축 요소가 있으면 기능 구현 전 확인 후 정리하기로 함.

확인 대상은 다음과 같음.

- 백엔드 실행 및 테스트 명령어
- 프론트엔드 Expo 실행 구조
- Prisma 및 PostgreSQL 연결 준비 상태
- `.env.example` 기반 로컬 환경변수 설정
- README의 실행 방법과 실제 명령어 일치 여부

---

## 3. 전체 레포 구조 점검 필요성 논의

환경 구축이 최종적으로 끝난 뒤, 본격적인 기능 구현 전에 현재 레포 전체 상태를 점검하기로 함.

점검 대상은 다음과 같음.

- 파일 및 폴더 구조
- `docs/requirements` 문서 내용
- `docs/design` 문서 내용
- `screenshots` 구조
- `src/frontend` 구조
- `src/backend` 구조
- GitHub Issue 내용
- Pull Request 내용
- README 실행 방법
- 테스트 보고서 예정 구조

정이량은 조장 역할로 전체 진행 상황과 작업 순서를 정리하기로 함. Codex 활용 결과는 필요할 때 조원들과 공유하며 진행하기로 함.

---

## 4. 1단계 제출 문서 검토 계획

요구사항 문서와 설계 문서 제출일이 다음 주 화요일까지이므로, 제출 전 두 문서를 다시 검토하기로 함.

교수님이 부록 파일 활용을 안내했으므로, 요구사항 문서와 설계 문서에 부록 파일을 연결하거나 통합하는 방식 검토 필요.

검토 기준은 다음과 같음.

- 요구사항 문서의 필수 항목 충족 여부
- 설계 문서의 아키텍처, 클래스 다이어그램, 시퀀스 다이어그램 포함 여부
- 이미지 및 PlantUML 원본 파일 경로 정상 여부
- 문서와 부록 파일의 연결성
- 제출용 PDF 분량과 가독성

## 5. AI 시뮬레이션 로그 부록 파일 분리 논의

현재 `docs/requirements/` 폴더에는 다음 파일이 있음.

- `requirements-document.md`
- `ai-user-interview-simulation.md`
- `usecase-diagram.puml`

과제 개요의 1단계 요구사항에는 AI 시뮬레이션 로그 첨부가 포함되어 있음. 따라서 별도 AI 시뮬레이션 로그 파일을 새로 만드는 방향을 검토하기로 함.

후보 파일명은 다음과 같음.

- `docs/requirements/ai-simulation-log.md`

해당 파일에는 AI를 활용해 요구사항, 페르소나, 유스케이스, 다이어그램, 설계 문서를 도출하고 수정한 과정을 요약하는 방향이 적절함.

## 6. requirements 폴더 문서 구조 정리 방향

기존 사용자 인터뷰 문서는 `ai-user-interview-simulation.md`로 정리하고, 인터뷰, 설문, 페르소나 중심 문서로 유지하는 방향이 적절하다고 판단함.

해당 문서는 사용자 그룹별 가상 인터뷰와 페르소나 도출 근거를 담는 부록 성격으로 정리함. 파일명 변경은 기존 링크가 깨질 수 있으므로 우선 보류하고, 필요 시 제목과 설명을 명확히 하는 방향을 검토함.

최종 요구사항 문서에는 `docs/requirements` 폴더 내 관련 부록 파일이 연결되도록 구성해야 함.

연결 대상 후보는 다음과 같음.

- AI 인터뷰 및 페르소나 시뮬레이션 문서
- AI 시뮬레이션 로그 문서
- 유스케이스 다이어그램 PlantUML 원본

## 8. Issue와 Pull Request 정리 방향

`docs/requirements`, `docs/design`, GitHub Issue, Pull Request 내용을 전체적으로 점검하기로 함.

정리 기준은 다음과 같음.

- 제목만 봐도 작업 내용을 알 수 있게 작성
- open Issue와 closed Issue 모두 확인
- open PR과 merged PR 모두 확인
- 어려운 용어는 의미가 흐려지지 않는 범위에서 간단 설명 추가 가능
- 문체는 높임말보다 간결한 작업 문서체로 통일

문체는 `~함`, `~임`, `~다`, `~이다` 중심으로 정리하기로 함.

예시는 다음과 같음.

- `배포 필요` → `배포해야함`
- `검토가 필요함` → `검토 필요`

## 9. 배포 관련 이슈 추가 계획

배포가 가까워지는 시점에 별도 Issue를 추가하기로 함.

배포 관련 Issue에는 다음 내용을 포함할 예정임.

- 배포 방식
- 프론트엔드 배포 방법
- 백엔드 배포 방법
- DB 호스팅 방법
- 환경변수 설정 방법
- 배포 서비스 선정 이유
- 기술 스택 선정 이유
- 팀원이 따라 할 수 있는 세팅 방법

현재 예상 배포 조합은 다음과 같음.

| 영역 | 후보 |
|---|---|
| Frontend | Vercel 또는 Expo 기반 배포 |
| Backend | Render |
| DB | Neon PostgreSQL |

최종 배포 방식은 실제 구현 진행 상황을 보고 확정 예정.

## 10. 교수님 질의응답 내용

교수님 질의응답을 통해 확인한 내용은 다음과 같음.

- 요구사항 문서와 설계 문서는 안내된 페이지 수를 초과해도 허용 가능함
- 수업 시간에 진행되는 팀별 면담은 평가에 직접 반영되기보다는 진행 상황, 작업 방법, 질의응답을 돕기 위한 목적임
- 보고서 제출 시 부록 파일을 잘 활용하는 것이 좋음
- 메인 제출 문서에는 필요한 부록 파일을 연결하거나 통합하여 활용하는 방식이 적절함
