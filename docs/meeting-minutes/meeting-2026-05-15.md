## 1. 브랜치 및 작업 흐름 정리

기존 작업 브랜치가 Pull Request 병합 이후 사라진 것으로 보여 혼동이 있었으나, 필요한 경우 같은 이름으로 로컬 브랜치를 다시 생성할 수 있음을 확인함.

작업 방식은 기존 협업 규칙대로 유지하기로 함.

- 각자 담당 브랜치에서 작업
- 작업 완료 후 Pull Request 생성
- main 브랜치에 직접 커밋하지 않음
- PR 리뷰 후 main에 병합

---

## 2. 1단계 산출물 검토 일정 논의

1단계 산출물은 저녁 8시경 온라인으로 검토하기로 함.

요구사항 문서를 기준 문서로 삼고, 설계 문서와 UML 다이어그램은 요구사항 문서의 기능 요구사항, 비기능 요구사항, 유스케이스 목록에 맞추어 정리하기로 함.

조원별 담당 영역은 다음과 같이 정리함.

| 조원 | 담당 영역 | 주요 작업 |
|---|---|---|
| 정이량 | 유스케이스 / 1단계 통합 | 유스케이스 다이어그램 작성, 1단계 산출물 정합성 확인 |
| 황대겸 | UML 다이어그램 | 클래스 다이어그램, 시퀀스 다이어그램, PlantUML 코드 및 PNG 정리 |
| 박지환 | 아키텍처 개요 | 시스템 아키텍처 개요 작성, 기술 스택 및 DB 선택 방향 검토, 외부 시스템 연동 구조 검토 |

---

## 3. 아키텍처 개요 문서 검토 방향

박지환이 아키텍처 개요 초안을 공유함.

검토 내용은 다음과 같음.

- DB 선택 방향
- 웹 기반 개발 방향
- JWT 기반 인증
- 로딩 화면 처리
- 데이터 최신화 주기
- 클라이언트와 서버의 처리 역할 분담

DB는 MySQL, MongoDB, 복수 DB 사용 가능성을 검토하되 아직 확정하지 않기로 함. 2단계 구현 전 요구사항과 구현 난이도를 기준으로 최종 검토하기로 함.

## 4. 2단계 구현 준비 방향

1단계 요구사항 문서와 설계 문서가 완료된 이후 개발 환경 구축과 베이스 코드를 정리하기로 함.

초기 환경 구축은 한 명이 주도하여 프로젝트 구조와 설정의 일관성을 유지하는 방향으로 논의함. 이후 기능별로 역할을 나누어 구현을 진행하기로 함.

## 5. UML 작업 진행 상황 공유

황대겸이 클래스 다이어그램과 시퀀스 다이어그램 작업 상황을 공유함.

진행 내용은 다음과 같음.

- 클래스 다이어그램 작성
- 시퀀스 다이어그램 작성
- PlantUML 코드 분리
- PNG 파일 생성
- 관련 Markdown 문서 작성
- `docs/design-uml` 브랜치 push 진행

기능 수가 많아 다이어그램이 복잡해지는 문제는 어느 정도 불가피하다고 판단함. 다만 최종 제출용 문서에서는 가독성을 고려하여 다이어그램 이미지와 설명을 함께 정리하기로 함.

## 6. GitHub Pull Request 작업 방식 확인

GitHub Pull Request 작업 방식은 README.md의 협업 규칙을 따르기로 함.

- 각자 작업 브랜치에서 커밋 후 PR 생성
- 담당자는 본인으로 지정
- 리뷰어는 본인을 제외한 조원 2명 지정
- 커밋은 작업 단위별로 자유롭게 진행
- PR은 base를 `main`, compare를 작업 브랜치로 설정
- 라벨은 필수는 아니지만 문서, 설계, 기능 분류용으로 활용 가능

## 7. 요구사항 문서 및 유스케이스 다이어그램 개선

요구사항 문서를 1단계 산출물의 기준 문서로 확정하기로 함.

유스케이스 다이어그램은 문서 가독성을 위해 다음 방향으로 개선하기로 함.

- PlantUML 코드는 요구사항 문서 본문에서 분리
- PlantUML 원본은 별도 `.puml` 파일로 관리
- 요구사항 문서에는 렌더링된 유스케이스 다이어그램 이미지만 삽입
- 다이어그램 안에서는 UC 번호를 제거하고 기능명만 표시
- 사용자와 관리자는 actor 형태로 표현
- AI 시스템과 외부 캘린더 시스템은 component 형태로 표현
- 액터별 연결선 색상을 다르게 설정

## 8. include / extend 관계 검토

유스케이스 다이어그램의 include / extend 관계를 검토함.

include는 필수 포함 관계에 사용하는데, 현재 기능 중 강한 include 관계로 보기 어려운 항목이 많다고 판단함.

- 학습 일정 관리와 칸반 보드 관리는 관련 기능이지만 필수 포함 관계는 아님
- 집중 모드 및 순공 시간 측정과 학습 통계 확인은 데이터 활용 관계에 가까움

최종적으로 include 관계는 사용하지 않기로 함. 필요한 부분만 extend 관계로 표현하기로 함.

반영 방향은 다음과 같음.

- 학습 통계 확인은 집중 모드 및 순공 시간 측정 이후 선택적으로 확인하는 흐름으로 보고 extend 관계로 표현
- 학습 추천 받기는 학습 통계 데이터를 기반으로 제공될 수 있으므로 학습 통계 확인과 extend 관계로 연결

## 9. 관리자 유스케이스 추가 논의

기존 관리자 역할이 게시판 관리에만 한정되어 있어 역할 범위가 좁다는 의견이 있었음.

관리자 유스케이스를 다음과 같이 보완하기로 함.

- 사용자 계정 관리 및 제재 추가
- 스터디 챌린지 관리 추가

다이어그램 배치는 다음 기준으로 정리하기로 함.

- 사용자 계정 관리 및 제재는 계정 기능 그룹에 배치
- 게시판 관리와 스터디 챌린지 관리는 커뮤니티 기능 그룹에 유지

## 10. 요구사항 문서 병합 및 최신화 요청

요구사항 문서는 아키텍처 개요와 UML 문서의 기준이 되므로 우선 병합하기로 함.

요구사항 문서 병합 이후 조원들은 main 브랜치를 최신화하고, UML과 아키텍처 개요 문서를 최신 요구사항 문서 기준으로 수정하기로 함.

## 11. AI 도구 활용 및 2단계 준비 논의

AI 도구 활용 현황과 2단계 준비 방향을 공유함.

- 박지환은 Gemini와 VSCode를 활용하여 문서 작업을 진행한다고 공유함
- 정이량은 Codex를 활용하여 레포 구조, 파일 구조, 브랜치, 커밋 히스토리 등을 분석하고 2단계 구현 준비를 진행할 계획이라고 설명함

2단계 시작 전 레포 전체 구조와 문서 내용을 분석한 뒤 베이스 코드와 환경 구축 방향을 결정하기로 함.

## 12. 회의 결과 요약

- 작업은 각자 담당 브랜치에서 진행하고 PR로 병합하는 방식을 유지함
- 요구사항 문서를 1단계 기준 문서로 확정함
- 아키텍처 개요는 DB, 인증, 클라이언트/서버 역할 분담 등을 2단계 구현 전 재검토하기로 함
- UML 문서는 요구사항 문서의 FR, NFR, UC 체계에 맞추어 정리하기로 함
- 유스케이스 다이어그램은 이미지와 PlantUML 원본을 분리하여 관리하기로 함
- include 관계는 사용하지 않고 필요한 부분만 extend 관계로 표현하기로 함
- 관리자 유스케이스를 보완하여 사용자 계정 관리 및 스터디 챌린지 관리 기능을 추가하기로 함

## 13. 향후 작업 계획

- 요구사항 문서 PR을 우선 검토 및 병합
- 병합 후 조원별 main 브랜치 최신화
- 아키텍처 개요 문서를 최신 요구사항 기준으로 수정
- UML 문서의 유스케이스 번호와 요구사항 ID 정합성 확인
- 1단계 산출물 최종 검토 후 2단계 구현 환경 구축 방향 논의
