## 2. 논의 내용

### 2.1 로그인 UX 정리

- 로그인 화면에서 음성 입력 버튼이 꼭 필요한지 다시 검토함.
- 로그인 단계에서는 음성 입력보다 기본 입력 흐름의 안정성과 명확성이 더 중요하다고 판단함.
- 초기 검토에서는 실제 backend auth 구조가 email 기반이므로 UI 문구만 `아이디` 중심으로 정리하는 방안을 우선 확인함.
- 이후 사용자 요구와 데모 계정 운영 기준을 고려해 `.com`이 붙은 이메일형 식별자보다 `loginId` 기반 로그인 체계가 더 적합하다고 판단함.
- 로그인/회원가입 화면 표기는 `아이디`로 통일하고, schema/API/seed/test/docs까지 loginId 기준으로 전환할 경우 별도 Issue/PR에서 migration과 seed 영향까지 함께 검토하기로 함.
- 비밀번호 입력란에는 eye icon 기반 show/hide toggle을 추가하여 사용자가 입력값 마스킹 상태를 직접 확인할 수 있게 하는 방향을 논의함.
- 해당 토글은 키보드 접근, focus 상태, 접근성 label을 함께 고려해야 함.

### 2.2 헤더 구조와 언어 드롭다운 개편

- 기능이 많아지면서 로그인 후 헤더의 탭이 늘어나고 정보 구조가 복잡해진 점을 확인함.
- 상단 메뉴는 정부24처럼 관련 메뉴를 묶어 하위 항목을 보여주는 방식까지 참고하되, 현재 프로젝트 규모에 맞춰 과도한 mega-menu는 피하기로 함.
- `프로필` 직접 탭은 중복 진입점이므로 제거하고, 우측 사용자 영역의 `마이페이지` 진입을 중심으로 정리하는 방향을 검토함.
- `마이페이지`, `로그아웃`, 다크모드 토글, 언어 전환 메뉴가 서로 겹치지 않도록 우측 영역의 시각적 우선순위를 정리하기로 함.
- 언어 선택은 버튼을 나열하는 방식보다 `Language` 드롭다운 또는 compact 메뉴형 구조가 더 적합하다고 판단함.
- 헤더 개편 시 기존 route/history/F5 복원 흐름을 깨뜨리지 않는 것을 우선 기준으로 둠.

### 2.3 접근성 음성 선택 및 미리듣기

- 읽어주기 기능에서 사용자가 선택한 목소리가 실제 음성 출력에 반영되지 않는 것처럼 보이는 문제를 확인함.
- 브라우저 SpeechSynthesis voice 목록은 비동기적으로 로딩될 수 있으므로 `voiceschanged` 이벤트와 선택값 반영 타이밍을 함께 점검해야 함.
- 각 목소리 옵션에는 작은 speaker icon을 두고, 사용자가 선택 전에 짧게 미리듣기할 수 있도록 개선하는 방향을 논의함.
- 미리듣기 중복 재생을 막기 위해 기존 재생을 cancel하거나 stop하는 처리도 필요함.
- 본 실행 읽어주기와 미리듣기 음성이 충돌하지 않도록 재생 상태를 분리해 관리해야 함.
- 음성 기능은 브라우저/기기 환경에 따라 지원 범위가 다르므로 실패 시 사용자 친화적인 안내를 유지하기로 함.
- 화면 읽기 기능은 전체 텍스트 읽기뿐 아니라 일시정지, 중지, 목소리 선택, 미리듣기까지 포함해 실제 사용 흐름 기준으로 보완이 필요함.
- 복습 알림은 접근성 설정 자체보다는 일정/알림 흐름과 연결하는 것이 더 자연스럽다는 의견이 있었음.

### 2.4 커뮤니티 레이아웃 개선

- 현재 커뮤니티 화면에서 오른쪽 공간이 비어 보이거나 정보 밀도가 어색하게 느껴지는 문제를 확인함.
- 게시판형 UI에 가깝게 목록, 검색, 필터, 상세 영역의 시선 흐름을 다시 정리하는 방향을 논의함.
- 기존 게시글 CRUD, 댓글, 반응, 북마크, 신고 흐름은 유지해야 하며, 레이아웃 변경으로 기능 회귀가 발생하지 않아야 함.
- 웹 화면에서는 목록과 상세를 함께 볼 수 있게 하되, 모바일에서는 상세 패널이 화면을 과하게 차지하지 않도록 반응형 구조를 유지하기로 함.
- 다국어 적용 이후 커뮤니티 버튼, 검색, 필터, empty state 문구도 함께 점검해야 함.

### 2.5 마이페이지 및 프로필 구조 개선

- 프로필 대시보드는 여러 정보를 담고 있어 한눈에 보기 어렵다는 의견이 있었음.
- 닉네임 변경과 비밀번호 변경 같은 계정 설정은 처음부터 모두 펼쳐두기보다 요약 카드, 탭, 접기/펼치기, 모달 등으로 정리하는 방향을 검토함.
- 기존 닉네임 변경/비밀번호 변경 API, validation, inline feedback은 유지하되 UI 정보 구조만 다듬는 것이 적절하다고 판단함.
- `마이페이지` 진입 개념과 프로필 대시보드 화면 구성이 일관되도록 용어와 배치를 맞추기로 함.
- "현재 사용 중인 닉네임입니다" 같은 즉시 피드백은 유지하되, 화면 전체가 복잡해지지 않도록 표시 위치와 상태를 조정하기로 함.

### 2.6 대시보드 일정 및 할 일 미리보기

- 메인 대시보드에서 일정/할 일을 바로 확인할 수 있으면 사용성이 좋아질 것으로 판단함.
- 단, 기존 보상, 학습 자극, 1초 퀴즈, 커뮤니티, AI 진입 영역과 충돌하지 않도록 compact preview 형태가 적절하다고 논의함.
- 오늘 일정, 가까운 일정, 진행 중 태스크, 마감 임박 태스크를 간단히 보여주는 방식이 우선 후보로 정리됨.
- 대시보드 미리보기는 전체 일정/칸반 기능을 대체하지 않고, 해당 화면으로 이동하는 짧은 연결 역할을 하도록 설계하기로 함.

### 2.7 일정 화면 구조 정리

- 일정 화면은 생성 폼, 월간 달력, 리마인더, 일정 목록, 우선순위 정보가 함께 있어 시선 흐름이 복잡해질 수 있음을 확인함.
- 정보 밀도는 유지하되, 섹션 제목과 요약 카드, 목록 순서를 정리해 화면 목적이 더 명확히 보이도록 개선하기로 함.
- 일정 생성 validation과 inline feedback은 유지하고, 입력 흐름과 결과 목록의 관계가 더 자연스럽게 보이도록 정리하는 방향을 논의함.
- D-Day 계획, 복습 알림, 기존 일정 목록이 서로 충돌하지 않도록 화면 구조를 유지해야 함.

### 2.8 다국어 전수 점검 필요

- 다국어 전환 기능이 추가된 뒤 일부 화면에서 한국어와 다른 언어가 한 문장 안에 섞이는 문제가 발생할 수 있음을 확인함.
- `지Fri`, `지週五`처럼 부분 문자열 치환으로 생기는 혼합 번역은 문장 단위 key 또는 locale 기반 formatter로 정리해야 함.
- Landing/Login 타이핑 문구, AppHeader, Dashboard, Profile, Statistics, Community, Friends, Schedule, TaskBoard, Reward, Shop, AI 화면을 전수 점검 대상으로 둠.
- AI mock/demo 응답, OCR/PDF mock 결과, 인증 만료, 사용량 초과, 설정 누락, 네트워크 오류 안내도 선택 언어를 반영하는지 확인해야 함.
- footer 문구는 언어에 따라 번역하지 않고 아래 고정 문구를 유지하기로 함.
  - `© 2026 CWNU Software Engineering Team 15 · 사각사각`
  - `Personalized Smart Edu Platform`
- English, 日本語, 中文은 Beta 언어로 표시하되, Beta는 언어 선택 UI에서만 작게 보여주는 방향을 유지하기로 함.
- Beta 표시는 번역을 대충 한다는 의미가 아니라 정식 검수 전 1차 지원 언어라는 의미로 설명하기로 함.
- 다국어 기능은 외국인 학생이나 외국 국적 사용자를 고려한 접근성 및 확장성 개선으로 설명할 수 있음.

### 2.9 local migration/seed 적용 승인 기준

- seed script 변경 사항은 팀에 공유하고, schema 변경 후에는 migration 적용 이후 seed를 실행해야 한다는 점을 재확인함.
- schema/migration 변경이 실제로 필요한 작업과 단순 UI 문구 변경을 구분하기로 함.
- auth 식별자 구조처럼 schema/API/seed 영향이 큰 변경은 충분히 검토한 뒤 별도 Issue/PR로 분리해야 함.
- 사용자는 개인 로컬 개발 DB 기준 migration 및 seed 적용을 승인했으나, 운영/공유 DB에는 임의로 실행하지 않는 원칙을 유지함.
- schema 변경 PR이 main에 merge된 뒤에는 최신 main 기준으로 `npx prisma migrate deploy`를 사용할 수 있음.
- seed 변경 PR이 main에 merge된 뒤에는 최신 main 기준으로 `npm run seed:dev`를 실행할 수 있음.
- DB 접속 정보와 인증 관련 민감정보는 출력하지 않기로 함.
- migration/seed 실행 방법은 관련 PR 본문 또는 코멘트에 명확히 남기기로 함.

### 2.10 사용자 경험 및 UI 개선 진행 상황

- 비밀번호 변경, 닉네임 변경, 프로필 대시보드, 통계 시각화, UI 애니메이션, hover/active/focus 마이크로 인터랙션 등 사용자 경험 개선 작업이 진행됨.
- 웹 기능은 큰 틀에서 완성 단계에 가까워졌으며, 이후에는 실제 사용자처럼 화면을 눌러보는 수동 QA가 중요하다고 정리함.
- 기능을 더 추가하는 것보다 화면 간 흐름, 입력 피드백, 접근성, 반응형, 다국어 적용 상태를 점검하는 안정화 작업이 필요함.

### 2.11 친구 기능 확장 방향

- 친구 추가 기능은 단순 친구 관리에 그치지 않고 후속 협업형 학습 기능의 기반 모듈로 활용하기로 함.
- 향후 스터디 보스 레이드, 친구 랭킹, 친구 기반 학습 자극 위젯, 협동 퀘스트와 연결할 수 있음.
- 1차 친구 기능은 요청/수락/거절/목록 확인을 안정화하고, 실시간 채팅이나 그룹 기능은 후속 범위로 분리함.

### 2.12 Issue/PR 운영 기준 공유

- 팀원별 작업은 GitHub Issue의 assignee 기준으로 확인하기로 함.
- 각자 맡은 Issue는 PR 본문에 `Closes #번호`를 명시해 merge 시 자동 close되도록 관리함.
- 작업 단위는 Issue, branch, PR로 분리하고, 하나의 작업은 하나의 PR로 관리하는 원칙을 재확인함.
- PR에는 주요 변경 내용, 검증 결과, 필요 시 스크린샷 또는 GIF를 포함하는 방향을 공유함.
- schema/migration/seed 변경이 있는 PR은 적용 방법과 실행 기준을 본문 또는 코멘트에 남겨야 함.

### 2.13 포인트 상점 asset 운영 방식

- 포인트 상점의 프로필 이미지, 배경, 칭호 등 소량의 미리 준비된 asset은 현재 프로젝트 규모에서는 frontend `src/assets`에 두는 방식이 적절하다고 판단함.
- 사용자가 업로드하는 이미지나 대규모 이미지 운영은 DB/스토리지 정책과 함께 후속으로 검토하기로 함.
- `assetUrl` 기반 local asset mapping은 현재 MVP에서 backend 데이터와 frontend asset을 연결하기에 적합한 방식으로 봄.

### 2.14 서비스 소개, 인트로, 스크롤 인터랙션 논의

- 서비스 소개 화면이 짧아 핵심 기능을 더 생동감 있게 보여주는 스크롤 인터랙션을 검토함.
- 인트로는 새로고침 시 다시 보일 수 있으나, 사용자가 끌 수 있는 옵션이나 “오늘 하루 그만 보기” 같은 제어가 필요하다고 논의함.
- 핵심은 화려한 효과 자체가 아니라 웹페이지가 살아있는 느낌을 주면서도 사용성을 해치지 않는 것임.
- 서비스 소개 섹션에는 핵심 기능을 순차적으로 보여주는 섹션 또는 슬라이드형 구성을 후속으로 검토함.

### 2.15 푸터 및 팀/프로젝트 정보 표시

- 서비스 소개 화면 하단에 저작권 문구와 GitHub 저장소 이동 아이콘을 배치하는 방향을 논의함.
- 팀명은 아직 확정하지 않았으므로 현재는 `CWNU Software Engineering Team 15 · 사각사각` 같은 중립적 표기를 사용하기로 함.
- 향후 팀원별 GitHub 프로필 링크를 푸터나 개발자 소개 영역에 넣는 방안도 검토할 수 있음.

### 2.16 배포 및 CI/CD 운영 기준

- Vercel frontend, Render backend, Neon PostgreSQL, GitHub Actions CI/CD 구조를 정리함.
- CI는 validate/generate/test/check를 수행하는 검증 단계임.
- CD는 main의 CI 성공 후 production DB migration을 적용하고 Render backend deploy hook을 호출하는 배포 단계임.
- Render backend는 Auto-Deploy를 끄고, GitHub Actions의 deploy hook 호출을 통해 배포하는 구조를 기준으로 함.
- seed는 자동화하지 않고, 로컬/데모 DB 대상이 안전할 때만 수동 실행하기로 함.
- 팀원이 배포 사이트에서 회원가입/로그인 테스트를 할 수 있으나, 실제 개인정보나 중요한 비밀번호는 사용하지 않도록 함.

### 2.17 후속 QA 및 마무리 방향

- 각 팀원은 실제 사용자처럼 웹을 사용하며 UI/UX 불편점, 레이아웃 문제, 기능 오류, 다국어 미적용 등을 찾아 Issue/PR로 보완하기로 함.
- #220 전체 화면 수동 QA와 #228 다국어 QA를 발표 전 점검 기준으로 활용함.
- 최종보고서, 발표자료, 데모 영상, 설치/사용 가이드 작성 준비 단계로 넘어가기로 함.

## 3. 결정 사항

| 항목 | 결정 |
|---|---|
| 로그인 음성 입력 | 로그인 화면에서는 제거하고 기본 입력 안정성을 우선 |
| 아이디 표기 | UI는 `아이디`로 통일하고, email 형식 대신 loginId 기반 전환을 별도 리팩터링 범위로 검토 |
| 비밀번호 입력 | eye icon 기반 show/hide toggle 추가 방향 |
| 헤더 구조 | 관련 메뉴를 그룹화하고, 언어 전환은 드롭다운/메뉴형으로 정리 |
| 프로필 탭 | 헤더 직접 탭은 제거하고 우측 사용자 영역의 `마이페이지` 진입 중심으로 정리 |
| 접근성 음성 | voice 로딩, 선택값 반영, 미리듣기, 재생 중복 방지 점검 |
| 커뮤니티 | 게시판형 정보 구조로 목록/상세/검색/필터 배치 개선 |
| 마이페이지 | 요약과 계정 설정 영역을 분리하고 설정 폼은 더 정돈된 구조로 개선 |
| 대시보드 | 일정/할 일 compact preview 추가 검토 |
| 일정 화면 | 폼, 요약, 목록, 리마인더 관계를 더 명확하게 정리 |
| 다국어 | 주요 화면과 AI/mock 문구를 전수 점검하고 혼합 번역 제거 |
| footer | 언어와 관계없이 영어/고유 문구 고정 |
| migration/seed | local DB 승인 범위 안에서만 적용하고, 운영/공유 DB에는 실행 금지 |
| 친구 기능 | 후속 협업형 학습 기능의 기반 모듈로 활용 |
| 포인트 상점 asset | 소량의 준비된 asset은 frontend `src/assets`와 local mapping 방식 유지 |
| CI/CD | CI는 검증, CD는 production migration 및 Render deploy trigger로 역할 분리 |
| seed 자동화 | workflow/Render/Vercel에 seed 자동 실행을 넣지 않음 |
