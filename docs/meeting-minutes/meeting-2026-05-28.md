## 2. 논의 내용

### 2.1 GitHub Actions 자동 검증 도입

- GitHub Actions를 통해 PR 생성 또는 업데이트 시 자동 검증을 수행하는 구조를 도입하기로 함.
- main 반영 시에도 자동 검증이 실행되도록 하여 main 브랜치의 안정성을 유지하기로 함.
- 자동 검증 대상은 Prisma schema 검증, Prisma Client 생성, 백엔드 테스트, 프로젝트 통합 check를 중심으로 함.
- 기본 실행 명령은 다음과 같이 정리함.
  - `npm run validate:prisma`
  - `npm --prefix src/backend run prisma:generate`
  - `npm test`
  - `npm run check`
- 프론트엔드는 자동 검증만으로 화면 품질을 모두 확인하기 어렵기 때문에 실제 화면 확인도 병행하기로 함.
- PR 생성 후 GitHub PR 화면의 Checks 또는 Actions 결과를 확인하는 방식으로 운영하기로 함.

### 2.2 테스트 문서와 테스트 코드 관리 기준

- 팀원은 기능 구현에 필요한 테스트 `.js` 파일을 자유롭게 생성하거나 수정할 수 있음.
- 단, `docs/test-report/test-report.md`는 테스트 수치와 보고서 정합성이 중요하므로 팀원이 임의로 수정하지 않는 방향으로 정리함.
- 테스트 보고서는 실제 테스트 수치, 검증 범위, 테스트 케이스가 변경될 때 정이량이 최종 정합성을 확인한 뒤 반영하기로 함.
- 구현 PR에서는 테스트 결과를 PR 본문에 명확히 남기고, 테스트 보고서 반영이 필요한 경우 별도로 검토하기로 함.

### 2.3 schema/migration 변경 고지 기준

- Prisma schema 변경 또는 migration 추가가 발생하면 PR 본문에 반드시 명시하기로 함.
- schema/migration 변경 PR은 팀 카카오톡에도 한 번 더 공유하여 팀원이 최신 main 반영과 로컬 migration 적용 여부를 알 수 있게 함.
- 운영 DB 또는 공유 DB에는 임의로 migration을 적용하지 않음.
- 팀원은 최신 main을 받은 뒤 필요한 경우 개인 로컬/개발 DB 기준으로 migration 적용 여부를 확인하기로 함.
- migration 포함 PR은 실제 DB 적용 여부, 실행하지 않은 DB 영향 명령, 팀원 로컬 적용 안내를 PR 본문에 남기는 것을 기준으로 함.

### 2.4 GitHub Actions workflow 관리 기준

- `.github/workflows/*.yml` 파일은 CI 동작에 직접 영향을 주므로 팀원이 임의로 수정하지 않는 방향으로 함.
- workflow 수정이 필요하면 별도 Issue 또는 PR에서 목적, 영향 범위, 검증 방법을 명확히 한 뒤 진행하기로 함.
- AI 에이전트에게도 workflow 파일을 임의로 변경하지 않도록 지시해야 함.
- 기존 작업 브랜치가 workflow 도입 이전에 생성된 경우, 최신 main 반영 여부를 확인한 뒤 PR을 갱신하기로 함.

### 2.5 CI 실패 대응 방식

- CI가 실패하더라도 코드를 바로 폐기하지 않고 실패 원인을 확인한 뒤 수정 commit을 추가하기로 함.
- 실패 로그는 PR의 Checks 탭 또는 저장소 Actions 탭에서 확인함.
- 실패 원인이 코드, 테스트, 문서, 환경 중 어디에 있는지 확인한 뒤 수정 범위를 결정함.
- CI 실패 상태를 무시하고 main에 merge하지 않는 것을 원칙으로 함.

### 2.6 AI 에이전트와 레포 운영 방어선

- AI 에이전트 작업과 원격 저장소 운영 안정성을 위해 4단계 방어선을 정리함.
  - 1차: AI 에이전트 폭주 방지 규칙
  - 2차: 최소 2명 리뷰 및 PR 검토
  - 3차: GitHub Actions CI check
  - 4차: 팀원별 주기적 백업
- AI 에이전트는 작업 보조 도구로 사용하되, 최종 판단은 팀원이 수행하기로 함.
- 원격 저장소에 영향을 주는 작업은 PR 기반으로 기록하고, 위험 명령은 단독 실행하지 않기로 함.

### 2.7 백업 기준

- AI 에이전트 작업이나 대규모 변경에 대비해 팀원별로 주기적인 백업을 남기기로 함.
- 백업 방식은 로컬 사본, 압축본, 별도 브랜치 등 팀원이 관리 가능한 방식을 사용할 수 있음.
- 백업은 AI 에이전트 오작동, 잘못된 merge, 예기치 않은 파일 변경에 대한 최후 방어선으로 봄.
- 특히 큰 기능 작업이나 workflow, schema, migration 관련 작업 전후에는 백업 상태를 확인하기로 함.

### 2.8 작업 브랜치 최신화와 팀원 작업 방향

- GitHub Actions workflow는 main에 반영된 뒤부터 적용되므로 기존 작업 브랜치에서는 최신 main 반영 여부를 확인해야 함.
- 기존 작업 브랜치에서 Actions 검증을 활용하려면 main의 최신 변경을 반영해야 함.
- 충돌이 복잡한 경우 workflow 파일은 main의 내용을 유지하고, 각자 작업 파일은 자신의 브랜치 변경을 유지하는 방식으로 정리할 수 있음.
- PR 생성 전 최신 main 반영 여부를 확인하고, 충돌이 예상되면 별도로 공유하기로 함.

### 2.9 모듈 개발 현황

- 황대겸은 음성/접근성 관련 모듈 작업을 계속 진행하기로 함.
- 고대비 UI 동작은 확인되었고, 음성 관련 문제는 추가 수정 대상으로 언급됨.
- 기존 디자인이 전체 반영되기 전에도 모듈 개발은 기본 디자인 기준으로 이어가기로 함.
- 정이량은 커뮤니티 이식과 백엔드/API 정합성 작업을 계속 관리하기로 함.

## 3. 결정 사항

- GitHub Actions 기반 PR 자동 검증을 팀 기본 운영 흐름에 포함함.
- 자동 검증 명령은 Prisma 검증, Prisma Client 생성, `npm test`, `npm run check`를 기준으로 함.
- 프론트엔드 변경은 자동 검증과 별도로 실제 화면 확인을 병행함.
- 테스트 `.js` 파일은 기능 담당자가 수정할 수 있으나, `docs/test-report/test-report.md`는 최종 정합성 확인 후 갱신함.
- schema/migration 변경은 PR 본문과 팀 카카오톡에 반드시 공유함.
- 운영/공유 DB에는 임의로 migration을 적용하지 않음.
- `.github/workflows/*.yml` 파일은 별도 Issue/PR 없이 임의 수정하지 않음.
- CI 실패 PR은 실패 원인을 확인하고 수정 commit으로 다시 검증함.
- AI 에이전트 작업은 4중 방어선 기준으로 관리함.
- 팀원별 백업을 주기적으로 남기고, 큰 변경 전후에는 백업 상태를 확인함.
