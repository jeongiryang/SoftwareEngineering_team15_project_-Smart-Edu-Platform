## 2. 주요 논의 내용

### 2.1 백엔드 기반 기능 구현 완료 공유

- Issue #60을 통해 2단계 백엔드 기반 기능 구현 완료 상태를 팀원들에게 공유함.
- 현재 백엔드는 인증, 사용자/프로필, 일정/태스크 API까지 기본 기반이 구현된 상태임.
- 공통 응답, 에러, 검증, async handler, 테스트 helper 구조도 정리됨.
- 개발용 seed script와 API 명세 문서도 추가됨.
- 이후 기능 구현 시 Issue #60과 `docs/api/api-spec.md`를 기준으로 참고하기로 함.

### 2.2 `test:db`, EACCES, Git branch와 DB branch 개념 정리

- `npm run test:db`는 실제 DB 연결이 되는지 확인하는 smoke test임.
- 내부적으로 Prisma Client가 `.env`의 `DATABASE_URL`을 사용해 Neon/PostgreSQL에 연결하고, 최소 query를 실행하는 방식임.
- `pg` 직접 `SELECT 1`은 Prisma를 거치지 않고 PostgreSQL 연결 자체를 확인하는 용도임.
- Git branch와 DB branch는 다른 개념임.
  - Git branch: `main`, `feat/...`처럼 코드 작업 단위
  - DB branch: `dev-main`, 개인 dev branch, production처럼 Neon DB 환경 단위
- 각자 기능 구현 시에는 Git 기능 브랜치에서 작업하되, `.env`는 본인 개인 Neon dev branch를 가리키도록 유지해야 함.
- EACCES가 발생하면 바로 코드 문제로 판단하지 않고, 아래 순서로 확인하기로 함.
  - `npm run check` 통과 여부
  - `npm install`, `npx prisma generate` 실행 여부
  - `.env`의 `DATABASE_URL`, `DIRECT_URL` 존재 여부
  - 본인 Neon dev branch 사용 여부
  - 네트워크, VPN, 방화벽 등 접속 환경
  - 해당 기능 브랜치에서 DB 연결 코드를 수정했는지 여부

### 2.3 AI API 비용과 무료 한도 리스크 논의

- AI 기능은 실제 API key를 사용해야 하며, ChatGPT 웹 구독이나 일반 AI 서비스 사용과는 별도의 API 사용량/요금 체계로 관리됨.
- Gemini API 무료 한도와 VS Code AI agent 확장 프로그램 사용 경험을 바탕으로, 무료 API만으로 충분히 안정적인 AI 기능을 제공할 수 있을지 우려가 제기됨.
- VS Code AI agent는 코드와 대화 맥락을 많이 포함해 요청하므로 일반 앱 기능보다 토큰을 많이 사용할 수 있음.
- 실제 앱에 AI 기능을 넣을 경우 백엔드에서 API key를 관리하고, 프론트에는 노출하지 않는 방향이 필요함.
- AI 기능은 바로 크게 구현하지 않고, 나중에 MVP 수준으로 작게 구현하는 방향이 적절하다고 판단함.
- 필요한 경우 여러 무료 API 또는 모델 fallback을 검토할 수 있으나, 모델별 응답 품질 차이가 발생할 수 있음을 인식함.
- AI API 사용 시 아래 기준이 필요함.
  - API key는 백엔드 `.env`에서만 관리
  - 프론트엔드에 API key 노출 금지
  - 호출 횟수 제한
  - 토큰/응답 길이 제한
  - 실패 시 fallback 응답 처리
  - 실제 API 호출은 시연용으로 최소화
  - 테스트는 mock 응답 중심으로 처리

### 2.4 학습 통계 기능 방향 정리

- 학습 통계 기능은 AI를 사용하지 않고 구현하는 방향으로 정리함.
- 학습 통계는 학습 시간, 집중 세션, 태스크 완료 여부, 날짜별/과목별 통계 등 구조화된 데이터를 기반으로 처리하면 됨.
- AI 요약 기능과 학습 통계 기능은 분리해서 생각하기로 함.

### 2.5 프론트 인증 화면 연결 및 웹 기준 구현

- 프론트 인증 화면 연결 작업을 통해 회원가입, 로그인, token 저장, 현재 사용자 확인, Dashboard 이동, 로그아웃 흐름을 구현함.
- 프론트 인증 화면 연결 후 회원가입, 로그인, Dashboard 이동, 로그아웃 흐름을 로컬에서 확인함.
- 현재 프론트 기본 화면은 최종 디자인이 아니라 인증 흐름 확인용 기본 화면임.
- 현재 프로젝트는 Expo 기반이지만, 과제 구현/시연/검증은 웹 기준으로 진행하는 것이 현실적이라고 정리함.
- 즉, 현재 기준은 "Web 중심 구현 및 검증"으로 봄.
- 프론트 인증 연결 후 팀원들은 백엔드와 프론트 dev server를 각각 실행해 로컬에서 확인하는 방식으로 진행함.
- Prisma Studio를 통해 실제 DB에 생성된 사용자 데이터를 확인할 수 있음을 공유함.

### 2.6 개발 순서 논의

- 황대겸은 API를 먼저 구현하고, 화면을 나중에 연결한 뒤, 마지막에 전체 디자인을 다듬는 순서를 제안함.
- 이에 대해 API 중심으로 먼저 잡는 방향은 적절하다고 판단함.
- 다만 API 전체를 완전히 끝낸 뒤 화면을 한꺼번에 붙이기보다는, 기능 단위로 API와 화면을 점진적으로 연결하며 검증하는 방식이 더 안전하다고 판단함.
- 팀은 남은 API를 먼저 정리하고, 각 기능 단위로 화면과 연동을 진행하는 방향에 동의함.
- 현재 인증/사용자/일정/태스크 API와 프론트 인증 연결은 완료된 상태이므로, 이후 남은 API와 화면을 순차적으로 진행하기로 함.
- 관리자 기능은 필수 사용자 기능은 아니므로 후순위 가능함.
- AI 학습 지원 MVP는 API key/요금/무료 한도 이슈로 신중하게 접근함.
- 현재 기준 개발 흐름은 아래처럼 정리함.
  - 핵심 API 구현
  - 해당 API를 사용하는 화면 연결
  - 기능 단위 동작 확인
  - 마지막에 전체 UI/UX 정리

### 2.8 커뮤니티/게시판 기능 재사용 방향

- 커뮤니티/게시판 기능은 기존 DB개론 과제 레포 `DatabaseLanguage_NodeJS_CWNU-Community`를 참고하여 재사용 가능성을 검토하기로 함.
- 해당 프로젝트에는 게시글 작성/조회/수정/삭제, 댓글, 좋아요 등 게시판 기능 구현 경험이 포함되어 있음.
- 다만 현재 `Smart Edu Platform`은 기존 프로젝트와 기술 구조, 인증 방식, Prisma schema, 프론트엔드 구조가 다르므로 그대로 복사하지 않고 현재 프로젝트 기준에 맞게 재설계해서 반영하기로 함.
- 재사용 가능한 요소는 아래와 같음.
  - 게시글 CRUD 흐름
  - 댓글 처리 흐름
  - 좋아요 처리 흐름
  - 게시글 목록/상세 화면 구성 아이디어
  - 게시판 API 테스트 관점
  - 기능 설명서/문서화 방식
- 현재 프로젝트에 반영할 때는 기존 공통 구조를 따라야 함.
  - `authMiddleware`
  - `req.user`
  - `AppError`
  - `validators`
  - `apiResponse`
  - `routes -> controller -> service -> repository -> prisma`
  - `docs/api/api-spec.md`
  - `docs/test-report/test-report.md`
- 커뮤니티 기능은 무작정 새로 만들기보다 기존 DB 과제 구현을 분석한 뒤, 필요한 기능만 선택적으로 이식하는 방향으로 진행하기로 함.
- 구현 전 기존 레포 분석 문서를 먼저 작성하는 방향이 적절함.

### 2.10 PR 검증 및 merge 운영 방식

- 앞으로 조원들이 기능을 구현해 PR을 올리면, 바로 main에 merge하지 않음.
- 정이량이 Codex를 통해 구조, 테스트, 문서, 오류, 리팩터링 필요 여부를 검토한 뒤 main에 반영하기로 함.
- main branch에 직접 push하지 않고 PR 기반으로 병합하는 흐름을 유지하기로 함.
- Squash/Rebase가 아니라 일반 Merge commit 기준을 유지함.
- PR 검증 시 확인할 기준은 아래와 같음.
  - 기존 공통 구조를 따랐는지
  - authMiddleware가 필요한 API에 적용되었는지
  - `req.user` 기준으로 사용자 데이터를 처리하는지
  - AppError, validators, apiResponse helper를 사용하는지
  - 테스트가 추가되었는지
  - `npm test`, `npm run check`가 통과하는지
  - `docs/api/api-spec.md`가 갱신되었는지
  - `docs/test-report/test-report.md`가 갱신되었는지
  - 비밀값 노출이 없는지
  - Prisma schema/migration을 임의로 수정하지 않았는지

### 2.11 Prisma Studio 사용법 및 확인 기준

- Prisma Studio는 DB 데이터를 편하게 확인/관리하는 도구로 설명됨.
- 확인 대상 테이블은 `users`, `user_profiles`, `study_schedules`, `study_tasks` 등임.
- 회원가입 시 기본적으로 `users` 데이터가 생성됨.
- `user_profiles`는 사용자 프로필 조회/수정 흐름에서 생성될 수 있음.
- `study_schedules`, `study_tasks`는 일정/태스크를 실제로 만들기 전에는 데이터가 없는 것이 정상임.
- `password_hash`는 암호화된 해시값이므로 정상이며, plain password가 저장되면 안 됨.
- seed 계정은 `npm run seed:dev`를 실행해야 생성됨.
- 테스트용 계정은 개인 dev DB에서는 필요에 따라 삭제해도 됨.
- 단, user 삭제 시 연결된 `user_profiles`, `study_schedules`, `study_tasks` 등 하위 데이터가 있으면 foreign key 때문에 삭제가 막힐 수 있음.
- 이 경우 하위 데이터를 먼저 삭제해야 함.
- production DB에서는 Prisma Studio 수정/삭제를 하지 않음.

### 2.12 Git branch와 DB branch 재정리

- Git branch와 DB branch는 별개임.
- Git branch는 기능 구현 단위 코드 브랜치임.
  - 예: `feat/...`, `chore/...`, `docs/...`
- DB branch는 Neon에서 분리된 데이터베이스 환경임.
  - 예: 개인 dev branch, `dev-main`, production
- 팀원들은 기능 구현 시 Git에서는 기능 브랜치를 새로 만들고, `.env`는 이미 배정된 본인 Neon dev branch를 사용하면 됨.
- 각자에게 제공된 `DATABASE_URL`, `DIRECT_URL`은 본인 Neon dev branch 기준으로 사용함.
- 기능 구현은 Git `main`에서 직접 하지 않고 기능 브랜치에서 진행함.

### 2.13 Repository 공개/보호 규칙 검토

- 팀원이 직접 기능 브랜치와 PR을 만들기 시작하면 사고 방지를 위해 repository 공개 상태와 branch protection rule 적용을 검토하기로 함.
- main branch에 직접 push하지 않고 PR 기반으로 병합하는 흐름을 유지하기로 함.
- Squash/Rebase가 아니라 일반 Merge commit 기준을 유지함.
- repository 공개 상태와 branch protection rule은 적용 완료가 아니라 검토/적용 예정으로 관리함.

### 2.14 DB 시간 표시 기준

- Prisma Studio나 DB에서 보이는 시간은 한국 시간과 다르게 보일 수 있음.
- DB 서버/Neon region 기준 또는 UTC 기준으로 표시될 수 있음.
- 앱/웹 화면에서는 필요한 경우 한국 시간 기준으로 변환해서 표시하면 됨.
- 따라서 Prisma Studio의 시간 표시가 한국 시간과 다르더라도 당장 기능 오류로 보지 않음.

### 2.15 schema / 컬럼 변경 규칙

- 현재 필요한 기본 schema는 어느 정도 세팅되어 있음.
- 기능 개발 중 필요한 필드나 모델이 추가로 필요하면 schema 변경은 가능함.
- 단, schema 변경이 있으면 PR 본문에 반드시 명시해야 함.
- 변경된 모델/필드, migration 여부, 영향받는 API를 PR에 적어야 함.
- 기존 필드 삭제, 관계 삭제, 타입 변경은 기존 API/테스트/프론트 의존성을 깨뜨릴 수 있으므로 원칙적으로 피함.
- 기존 필드 삭제나 관계 변경이 꼭 필요하면 별도 논의 후 진행함.
- 기존 기능에 영향을 줄 수 있는 schema 변경은 Codex 기반 검증 후 merge하기로 함.
- Prisma migration을 임의로 실행하거나 production DB에 적용하지 않음.
- `prisma migrate dev`는 개인 dev branch 또는 dev-main에서만 사용함.
- production DB에서는 `migrate dev`, `seed:dev`, `test:db` 실행 금지.
- schema 변경 PR에는 아래 항목을 반드시 포함해야 함.
  - 변경 사유
  - 변경된 모델/필드/관계
  - 생성된 migration 파일 여부
  - 영향받는 API
  - 문서 갱신 여부
  - 테스트 결과

## 3. 결정 사항

| 항목 | 결정 |
|---|---|
| 구현/시연 기준 | Expo 기반이지만 Web 중심으로 구현/검증 |
| 프론트 인증 흐름 | 회원가입, 로그인, token 저장, 현재 사용자 확인, Dashboard 이동, 로그아웃까지 구현 |
| Git branch와 DB branch | Git 기능 브랜치와 Neon DB branch는 별개로 관리 |
| DB 확인 도구 | Prisma Studio를 개인 dev DB 확인용으로 사용 |
| DB 시간 표시 | Prisma Studio 시간은 한국 시간과 다를 수 있으며, 화면에서는 필요 시 변환 |
| 테스트 계정 | 개인 dev DB에서는 필요에 따라 삭제 가능 |
| seed 계정 | seed script 실행 시 생성되며, 가능하면 유지 |
| 학습 통계 | AI 없이 시간/태스크/집중 세션 기반 통계로 구현 |
| AI 기능 | 후순위로 두고 MVP 수준으로 제한적으로 검토 |
| AI API key 관리 | 백엔드 `.env`에서만 관리, 프론트엔드 노출 금지 |
| 개발 순서 | API 중심으로 기능을 잡되, 기능 단위로 화면 연결과 검증을 병행 |
| 커뮤니티/게시판 | 기존 DB개론 과제 구현을 참고해 현재 프로젝트 구조에 맞게 재설계/이식 |
| 관리자 기능 | 사용상 필수 기능은 아니므로 후순위 가능 |
| schema 변경 | 필요 시 가능하지만 PR에 반드시 명시하고 검증 후 merge |
| 기존 필드 삭제/관계 변경 | 의존성 문제 가능성이 있어 신중하게 처리 |
| 역할 분담 | 박지환은 학습 노트 API/집중 시간·통계 API, 황대겸은 관리자 기능/AI MVP 방향으로 진행 |
| UI/UX | 마지막에 팀 전체가 함께 정리 |
| PR 운영 | 조원 PR은 Codex 기반 검증/보완 후 main merge |
| 비밀값 관리 | DB URL, API key, JWT token 원문을 GitHub/문서/카톡에 작성하지 않음 |
