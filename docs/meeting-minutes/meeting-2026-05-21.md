## 2. 주요 논의 내용

### 2.1 요구사항 문서 구조

- 요구사항 문서에서 요구사항 추적표보다 유스케이스 목록과 유스케이스 다이어그램이 먼저 제시되는 구조가 더 자연스럽다고 판단함.
- 요구사항 추적표는 `FR`, `NFR`, `UC` 간 연결을 보여주는 표이므로, 유스케이스 ID가 먼저 정의된 뒤 추적표가 나오는 흐름으로 정리하기로 함.
- 요구사항 ID와 유스케이스 ID 자체는 변경하지 않고 섹션 순서와 목차만 정리하기로 함.

### 2.2 아키텍처 문서 정합성

- `architecture-overview.md`의 프론트엔드 MVC 설명이 모바일 애플리케이션만 강조하고 있어 Web/Mobile 클라이언트를 모두 포함하도록 표현을 보완하기로 함.
- `design-document.md`에는 External Integration 계층이 포함되어 있으므로, `architecture-overview.md`의 계층형 아키텍처 설명에도 외부 연동 계층을 반영하기로 함.
- `architecture-overview.md`의 일부 모듈 설명에서 문장 끝에 붙은 요구사항 ID 표기는 별도 추적표에서 관리하는 것이 더 일관적이라고 판단함.
- 굵은 글씨 강조 문장과 주변 문장이 붙어 보이는 부분은 Markdown 미리보기 기준으로 줄바꿈과 띄어쓰기를 정리하기로 함.

### 2.3 클래스 다이어그램 분할 구조

- 전체 클래스 다이어그램은 7개 도메인 구조로 구성되어 있으나, 기존 분할 클래스 다이어그램에서는 학습 노트/퀴즈와 AI 학습 지원이 하나로 묶여 있어 전체 다이어그램 구조와 완전히 대응되지 않는다고 판단함.
- 분할 클래스 다이어그램을 전체 다이어그램 기준에 맞춰 다음 7개 도메인으로 정리하기로 함.

  - 사용자/인증
  - 학습 일정/태스크
  - 학습 노트/퀴즈
  - AI 학습 지원
  - 커뮤니티/챌린지/관리자
  - 집중 시간/통계
  - 보상

- 기존 노트/퀴즈/AI 통합 분할 다이어그램은 학습 노트/퀴즈와 AI 학습 지원 다이어그램으로 분리하기로 함.
- 전체 클래스 다이어그램 원본과 이미지는 기준 산출물로 유지하고, 분할 다이어그램만 정합성 보완 대상으로 삼기로 함.

### 2.4 설계 문서 가독성

- `design-document.md`의 주요 클래스 설명이 마지막 섹션에 모여 있어, 각 도메인별 클래스 다이어그램을 볼 때 해당 도메인의 핵심 클래스를 바로 확인하기 어렵다고 판단함.
- 주요 클래스 설명은 각 도메인별 클래스 다이어그램 이미지와 링크 표 아래에 배치하는 방식으로 정리하기로 함.
- 기존 클래스 의미와 요구사항 연결은 유지하고, 설명 위치만 도메인별로 분산하기로 함.

### 2.5 앱/웹 서비스명 및 아이콘

- 프로젝트명은 기존과 같이 `Smart Edu Platform`으로 유지하기로 함.
- 실제 앱/웹 서비스명은 `사각사각`으로 확정함.
- `사각사각`은 필기 소리와 학습 기록 이미지를 연상시키는 이름으로, 개인화 학습 관리 앱의 성격과 어울린다고 판단함.
- 앱 아이콘은 연필이 글씨를 쓰는 듯한 이미지와 지우개/필기 느낌을 중심으로 확정함.
- 확정 아이콘 이미지는 [screenshots/sagaksagak-app-icon.png](../../screenshots/sagaksagak-app-icon.png) 경로로 관리하기로 함.

## 3. 결정 사항

- 요구사항 문서는 유스케이스 다이어그램 섹션이 요구사항 추적표보다 먼저 나오도록 정리함.
- `architecture-overview.md`와 `design-document.md`의 계층 구조를 External Integration 계층 기준으로 맞춤.
- 분할 클래스 다이어그램은 전체 클래스 다이어그램의 7개 도메인 구조에 맞춰 정리함.
- `design-document.md`의 주요 클래스 설명은 각 도메인별 클래스 다이어그램 하위로 배치함.
- 프로젝트명은 `Smart Edu Platform`으로 유지하고, 실제 앱/웹 서비스명은 `사각사각`으로 확정함.
- 앱 아이콘 이미지는 `screenshots/sagaksagak-app-icon.png`로 관리함.
