## 2. 논의 내용

### 2.1 스크린샷 기록 및 관리

- 기능 구현 과정에서 화면 변화와 구현 진행 상황을 추적할 수 있도록 스크린샷을 지속적으로 남기기로 함.
- 최종 제출용 이미지뿐 아니라, 필요 시 중간 구현 상태를 확인할 수 있는 raw 성격의 스크린샷도 보관하는 방향을 검토함.
- raw 스크린샷과 최종 제출 이미지는 성격이 다르므로 후속 작업에서 폴더 구조와 파일명 규칙을 구분해 관리하기로 함.
- 구체적인 저장 구조는 추후 확정하되, 구현 변화 과정이 누락되지 않도록 기록하는 것을 기본 원칙으로 함.

### 2.2 남은 모듈 구현 방향

- 1단계 제출 이후에도 2단계 구현을 계속 진행하기로 함.
- 남은 기능은 모듈 단위로 나누어 Issue, branch, PR 단위로 관리하기로 함.
- 현재 올라온 open PR은 이후 검토를 진행하고, 문제가 없으면 빠르게 merge하는 방향으로 정리함.
- 단, 기존 운영 원칙에 따라 PR은 바로 신뢰하지 않고 변경 파일, 테스트 결과, 문서 반영 여부, 예상 밖 변경 여부를 확인한 뒤 merge하기로 함.

### 2.3 PR 및 API 변경 관리 기준

- API 삭제, 변경, 추가가 있는 PR은 본문에 변경 사항을 반드시 명시하기로 함.
- API 변경 내용에는 endpoint, method, request body, query parameter, response, error 정책, 인증 필요 여부를 포함하기로 함.
- API 변경이 있는 PR은 리뷰어가 API 명세와 실제 구현의 정합성을 함께 확인할 수 있도록 작성하기로 함.
- 팀원은 좋은 아이디어가 있으면 Issue 또는 PR로 자유롭게 제안하되, main에는 직접 반영하지 않고 PR 검토 절차를 거쳐 반영하기로 함.
- 아이디어성 PR도 변경 의도, 범위, 영향 파일, 검증 결과를 명확히 작성하는 것을 원칙으로 함.

### 2.4 API 명세서와 테스트 보고서 관리 기준

- API 관련 변경이 발생하면 우선 `docs/api/api-spec.md`를 실제 구현과 맞게 반영하는 것을 원칙으로 함.
- 단순 API 명세 정리 작업에서는 `docs/test-report/test-report.md`를 불필요하게 수정하지 않기로 함.
- 실제 테스트 수치, 테스트 범위, 테스트 케이스가 바뀌는 구현 PR에서만 테스트 보고서를 갱신하기로 함.
- API 명세만 필요한 작업과 테스트 보고서 갱신이 필요한 작업을 구분하여 문서 변경 범위를 관리하기로 함.

### 2.5 AI 기능 이미지 업로드 검토

- AI 기능에서 이미지 업로드를 지원할 수 있는지 후속 기능 후보로 검토하기로 함.
- 이미지 기반 질의, 학습 자료 이미지 입력, 학습 보조 자료 분석 가능성을 검토 대상으로 둠.
- 다만 현재 즉시 구현 범위로 확정하지 않고, API와 프론트엔드 영향 범위를 확인한 뒤 별도 Issue와 PR로 분리하기로 함.

### 2.6 프로필 화면 및 개인 대시보드 방향

- 프로필 화면을 단순 사용자 정보 표시 화면이 아니라 개인 대시보드 성격으로 확장하는 방향을 논의함.
- 사용자가 프로필을 누르면 최근 활동, 학습 요약, 작성한 게시글과 댓글, 참여 기록 등 개인 활동을 한눈에 볼 수 있는 구성을 검토함.
- 해당 기능은 커뮤니티, 학습 통계, 보상 기능과 연결될 수 있으므로 후속 프론트엔드/UI 작업에서 구체화하기로 함.
- 사용자 활동 요약 허브 역할을 할 수 있도록 화면 정보 구조와 접근 흐름을 함께 검토하기로 함.
